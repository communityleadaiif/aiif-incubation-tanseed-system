# AIIF Incubatee Management & TANSEED Documentation System
## Project Context / Coding-Agent Handoff

**Organisation:** AJK Innovation Incubator Foundation (AIIF)  
**Location:** Coimbatore, Tamil Nadu, India  
**Project purpose:** Build a structured digital system for managing AIIF incubatees, incubation documentation, mentors, milestones, evidence, government funding support and TANSEED-related records.

---

# 1. ORGANISATIONAL CONTEXT

AJK Innovation Incubator Foundation (AIIF) is a Section 8 company and the innovation/incubation hub associated with AJK Group of Institutions.

AIIF's incubation activities may include:

- Startup identification and admission

The intended long-term objective is to move from informal incubation administration to a documented, auditable institutional incubation system.

# 2. CURRENT BUSINESS PROBLEM

One AIIF incubatee has reached the final stage of TANSEED.

Historically, AIIF has supported the startup, but a formal incubation documentation trail was not created at the beginning. There is therefore a documentation gap.

The correct approach is NOT to fabricate or backdate documents.

Instead:

1. Capture genuine historical interactions/support using available evidence.
2. Create a Historical Incubation Support Record.
3. Conduct a current formal incubation evaluation.
4. Obtain Incubation Committee approval.
5. Execute a formal Incubation & Startup Support Agreement from the actual execution date.
6. Create a complete Startup Master File.
7. Issue factual institutional/TANSEED support letters.
8. Establish a standard SOP so future incubatees follow the same process from Day 1.

Important distinction:

- "Previously associated with / received support from AIIF" is different from
- "Formally admitted as an AIIF incubatee on DATE."

The system must preserve this distinction.

# 30. CRITICAL DATA INTEGRITY & RELIABILITY SPECIFICATION

## 30.1 Purpose

Data correctness is a PRIMARY system requirement.

The system must be designed so that records cannot become interchanged, orphaned, duplicated or silently lost as a result of sorting, filtering, importing, editing, refreshing, concurrent use, deployment or application errors.

A visually correct UI is NOT sufficient. The underlying database, API and data lifecycle must be correct.

---

## 30.2 SINGLE SOURCE OF TRUTH

The production database is the authoritative source of truth.

The following must NEVER be the sole production source of truth:

- Browser localStorage
- sessionStorage
- frontend JavaScript arrays
- React/Vue/etc. component state
- temporary JSON files
- CSV files
- Excel files
- browser cache

These may be used for temporary UI state, import/export or offline workflows only.

Recommended architecture:

Frontend
→ Authenticated API / Server
→ Relational Database
→ Automated Backup / Recovery

---

## 30.3 PERMANENT UNIQUE IDENTIFIERS

Every entity must have a stable unique primary key.

Examples:

Student:
STU-2026-000001

Founder:
FND-2026-000001

Startup:
AIIF-INC-2026-0001

Mentor:
MNT-2026-000001

Team:
TEAM-2026-000001

Application:
APP-2026-000001

Evaluation:
EVA-2026-000001

Document:
DOC-2026-000001

The identifier must not depend on:

- name
- email
- phone
- department
- row number
- array index
- registration order in a UI
- spreadsheet row

IDs must remain stable for the life of the record.

---

## 30.4 FIELD OWNERSHIP

A person's information belongs to that person's master record.

Example:

Student STU-2026-000047 owns:

- Name
- Gender
- Email
- Phone
- Date of birth where collected
- Department
- Programme
- Year
- Admission information

Other modules must reference:

student_id = STU-2026-000047

They must NOT independently duplicate and maintain:

student_name
student_email
student_gender

unless there is a specific historical/snapshot requirement.

This prevents:

"Name from Student A + Email from Student B + Gender from Student C"

type failures.

---

## 30.5 RELATIONAL INTEGRITY

All relationships must use database foreign keys.

Examples:

TeamMember.student_id → Student.id

Evaluation.startup_id → Startup.id

MentorAssignment.mentor_id → Mentor.id

MentorAssignment.startup_id → Startup.id

Milestone.startup_id → Startup.id

Document.startup_id → Startup.id

The database must reject references to non-existent parent records.

Orphan records must not be silently created.

---

## 30.6 DATABASE CONSTRAINTS

Critical fields must have appropriate:

- PRIMARY KEY
- FOREIGN KEY
- UNIQUE
- NOT NULL
- CHECK constraints
- appropriate data types

Do not rely only on frontend validation.

Frontend validation improves user experience.

Database validation protects data.

Both are required.

---

## 30.7 TRANSACTION SAFETY

Multi-step operations must use database transactions.

Example:

Creating a team with six students should be atomic.

Either:

ALL valid records are created

OR

NONE are created.

Never leave a partially-created team because step 4 of 6 failed.

Same principle applies to:

- imports
- evaluations
- application submissions
- agreement execution
- mentor assignments
- bulk updates
- migration
- deletion/archive operations

---

## 30.8 CONCURRENCY

The system must handle two authorised users editing the same record.

Example:

User A opens Student STU-00047.

User B opens Student STU-00047.

User A changes email.

User B changes department.

The system must not silently overwrite User A's change when User B saves.

Use appropriate optimistic locking/version fields or equivalent concurrency control.

Every mutable record should have a version or updated_at mechanism.

---

## 30.9 SOFT DELETE

Important institutional records should not be permanently deleted through normal UI actions.

Use:

- active
- archived
- deleted/soft-deleted

with:

- deleted_at
- deleted_by
- deletion_reason

Only highly authorised administrators may perform permanent deletion, and permanent deletion should be exceptional.

---

- audit_id
- user_id
- action
- entity_type
- entity_id
- timestamp
- old_value
- new_value

Examples:

UPDATE STUDENT

Normal users must not be able to edit or delete audit records.

---

## 30.11 BULK IMPORT SAFETY

No spreadsheet/CSV import should write directly into production without validation.

Required workflow:

UPLOAD
→ PARSE
→ VALIDATE
→ DUPLICATE CHECK
→ RELATIONSHIP CHECK
→ PREVIEW
→ USER CONFIRMATION
→ TRANSACTIONAL IMPORT
→ RECONCILIATION
→ AUDIT LOG

Before import, display:

- total rows
- valid rows
- invalid rows
- duplicate rows
- missing required fields
- invalid references
- rows that will be updated
- rows that will be created

The user must be able to download an error report.

---

## 30.12 IMPORT RECONCILIATION

After import, show:

Records submitted
Records created
Records updated
Records skipped
Records rejected
Duplicates
Errors
Final database count

Example:

Records submitted: 1,000
Created: 230
Updated: 15
Skipped: 3
Rejected: 2

The numbers must reconcile.

If reconciliation fails, the transaction must roll back.

---

## 30.13 DUPLICATE DETECTION

The system should detect likely duplicates using configurable matching rules.

Potential signals:

- same email
- same phone
- same institutional ID
- same government/company registration ID
- exact or near-exact name
- same founder + company combination

The system must NOT automatically merge uncertain records.

Instead:

POSSIBLE DUPLICATE
→ REVIEW
→ MERGE / KEEP SEPARATE

Any merge must create an audit record.

---

## 30.14 DATA NORMALISATION

Use controlled master data where possible.

Examples:

Department should reference a Department entity rather than arbitrary text.

Gender should use configured values rather than dozens of spellings.

Programme should reference a Programme entity.

Academic year should use a controlled value.

This reduces:

"BCA"
"B.C.A"
"BCA "
"BCA AI"
"Bca"

being treated as unrelated categories.

Where free-text is necessary, preserve the original value.

## 30.16 DATA ENTRY UX

For critical records:

- Never auto-shift fields based on row order.
- Never use array index as identity.
- Never silently replace values.
- Show record ID prominently.
- Show "Last updated" information.
- Show who last updated the record.
- Confirm high-impact changes.
- Provide undo/restore where possible.
- Use dropdowns for controlled data.
- Validate email and phone formats.
- Warn about duplicate email/phone before save.

---

## 30.17 AUTOSAVE SAFETY

If autosave is implemented:

- Never overwrite a newer server version with an older browser version.
- Use record version numbers.
- Show save status.
- Show failed-save errors.
- Do not tell the user "Saved" until the server confirms persistence.

Preferred states:

Saving...
Saved at 13:42
Save failed — retry

Never silently fail.

---

## 30.18 OFFLINE / NETWORK FAILURE

If internet/network connectivity is lost during a critical operation:

- Do not claim success.
- Do not duplicate the operation on automatic retry without idempotency protection.
- Clearly show the user whether the operation succeeded, failed or is pending.
- Use idempotency keys for operations that may be retried.

---

## 30.19 API SAFETY

The backend must validate every incoming request.

Never trust:

- hidden form fields
- frontend role claims
- client-generated IDs
- client-side validation
- browser state

Authorisation must be enforced server-side.

---

## 30.21 BACKUP & RECOVERY

Production data must have automated backups.

Minimum recommended architecture:

- automated daily backup
- frequent incremental/point-in-time recovery where supported
- separate backup storage
- backup retention policy
- periodic restore test

A backup that has never been successfully restored is not considered proven.

At least periodically, perform:

BACKUP
→ RESTORE TO TEST ENVIRONMENT
→ VERIFY RECORD COUNTS
→ VERIFY SAMPLE RECORDS
→ VERIFY RELATIONSHIPS

---

## 30.22 DATABASE MIGRATIONS

Schema changes must use version-controlled migrations.

Never manually change production schema without recording the migration.

Every migration must be:

- numbered/versioned
- reversible where practical
- tested on a staging copy
- documented

Never casually delete columns or tables because the UI no longer uses them.

Use anonymised/synthetic data for testing where possible.

# 32. CODING AGENT HARD RULES

The coding agent must NOT:

1. Replace a database with localStorage merely to make development easier.
2. Use array indexes as record IDs.
3. Store related entities only by copied names.
4. Silently discard failed writes.
5. Silently overwrite newer data.
6. Delete database records during refactoring without explicit migration.
7. Reset the production database during deployment.
8. Seed test data into production.
9. Change database schema manually without migration.
10. Auto-merge uncertain duplicate records.
11. Claim a save succeeded before server confirmation.
12. Allow frontend-only authorisation.
13. Remove fields because they appear unused without checking dependencies.
14. Rewrite existing production records merely to fit a new schema.
15. Build the UI first and postpone data architecture.

# 33. GO-LIVE PRINCIPLE

The system should be considered ready only when:

**Correctness > Convenience > Visual polish**

A beautiful dashboard with unreliable data is a failed incubator system.

A simple dashboard with reliable, recoverable and auditable data is acceptable for MVP.

# 34. MASTER PROJECT DECISION

The AIIF system is an institutional system, not a disposable event website.

It must therefore be designed for:

- multi-year operation
- multiple administrators
- multiple startups
- thousands of student/startup/mentor records
- historical records
- government scheme documentation
- audit requirements
